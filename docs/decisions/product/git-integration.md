# Git integration: history as a substrate surface, the VCS behind a seam, a disciplined write path

- **Status:** adopted — interviewed, drafted, and adopted 2026-07-29 (batched interview)
- **Decided / updated:** 2026-07-29
- **Layer:** both — the substrate wraps the version-control boundary and exposes history; surfaces render timelines and invoke the write verbs
- **Config vs. invariant:** *Invariant* — the store is **fully versioned** and its history is a **substrate surface**: per-note timeline, version diff, and who-or-what-wrote-this attribution are substrate operations, never per-surface re-derivation; **authorship is resolved from version history**, never parallel hand-maintained bookkeeping; the version layer is addressed through a **seam** defined by required properties (full history, hook-able boundary, host-neutral, plain-file native) rather than one tool's API; **read-side always works** over whatever history exists — the product never requires owning the commit path; when the tool *does* own the path, writes are **verb-mediated, validated at the boundary, and scoped** — a commit takes exactly its author's files, never a concurrent writer's. *Config-point* — the concrete VCS (git is the default and the only current implementation of the seam); the commit posture as intelligent defaults on hooks (message grammar, attribution scheme, gate tiers, commit cadence); remotes and sync behavior (which remote, auto push/pull, remote-state display, separate channels for version-ignored personal state); which surfaces expose commit affordances at all.

> **Boundary.** [markdown-flavor](markdown-flavor.md) is what makes this PDR possible — plain files are the only store every version-control tool already speaks; its round-trip contract is what keeps diffs meaningful. This PDR owns the *version dimension*: history as a view, and the posture of the write path. The [authorship](authorship.md) PDR (queued, interview-first) *consumes* the attribution substrate established here — it owns what authorship *means* in the document (fences, spans, ownership), including whether history-derived attribution can replace in-band marking.

## 👁️ Intent

A knowledge corpus accrues for decades and is increasingly written by many hands — the user across years, agents acting on their behalf, eventually collaborators. Three needs follow, and they are trust needs, not features: **recoverability** (no edit, however botched, can lose what was there before), **legibility of change** (what changed, when, in what unit, and why), and **provenance** (which hand — human, agent, tool — wrote this line). Maintaining any of these by hand is bookkeeping nobody sustains; a versioned store provides all three as a byproduct of writing — *if* the product treats history as a first-class read surface and keeps the write path disciplined enough that history is worth reading.

## 🎨 Design

**History is a substrate surface, not a feature.** The same contract shape as [wikilink-ui](wikilink-ui.md)'s resolution bundle: the substrate owes the *facts* — a note's timeline of versions, the diff between any two, the attribution of each change — as operations every surface builds on, and each surface chooses its rendering (a history pane, a blame gutter, an agent's structured answer). No surface re-derives history its own way; all of them agree because there is one answer.

**The VCS sits behind a seam.** The product's dependency is on *properties*, not a tool: full history of plain files, a hook-able boundary where checks can run, host-neutrality (any remote, or none), and cheap distribution. The contract is written against those properties so the version layer is pluggable — version-control tools keep being invented, and a knowledge corpus should outlive any of them. Git is the default and the obvious choice: it is the one tool with universal tooling, universal hosting, and a multi-decade record — but it enters as the seam's first implementation, not as the contract.

**Authorship rides version history.** A multi-hand corpus must answer "who wrote this" — and the answer is *derived from the version record*, where every change already carries its author, never from parallel metadata someone must remember to update. Attribution that rides the write path cannot drift from the writing; attribution kept beside it always can. This is the substrate a full authorship-and-ownership model builds on, and it is why version control is that model's prerequisite rather than its neighbor. Two consequences this PDR fixes: the attribution grammar should carry **full actor identity** (human, agent, skill, tool — not just a name), and the merge posture must **preserve per-change attribution** (no history-flattening merges). What it deliberately leaves open: whether history-derived span attribution can *replace* in-document authorship marking — that question, with its tradeoff (in-band plain-file legibility and span survival vs. derived, drift-proof provenance), belongs to the [authorship](authorship.md) PDR.

**When the tool owns the write path, writes are verb-mediated, validated, and scoped.** Mutations go through substrate verbs that validate at the boundary (the hook-able seam is *for* this: structural checks always, deferred-completeness checks at promotion — the gate tiers are [lifecycle](lifecycle.md)'s and [inbox-workflow](inbox-workflow.md)'s to define) and commit with content-derived, typed messages — so the log reads as a journal of *what happened to the knowledge*, queryable by actor and act. Notes commit at birth and accrue history rather than landing finished: work that sits uncommitted is invisible to every other reader — human, agent, audit — and unprotected; incremental history is also simply *more* history, and history is the point. Because many writers share one working tree as the normal case, scoping is an invariant of the verbs: a commit takes exactly the files its act touched — sweeping a concurrent writer's in-flight work into a stranger's commit is a defect class the verbs eliminate by construction. The whole posture — grammar, gate assignment, cadence — ships as intelligent defaults on hooks, not hard-coded ritual: it is the recommended discipline, and a vault may tune every piece.

**Guest mode: the product never requires owning the commit path.** A knowledge base may live inside a repository whose version workflow belongs to something larger — documentation inside a codebase, notes inside a team monorepo. The read side is unconditional: history, diff, and attribution verbs work over whatever history exists, however it was made. The write side degrades gracefully: commit verbs and gates are the default when the tool owns the boundary, and become optional, advisory checks when the host workflow owns it. A tool that insisted on its own commit ritual would exclude exactly the embedded uses where a disciplined knowledge layer is most valuable.

**Sync is the remote, surfaced.** The product runs no hosted backend: sharing, backup, and multi-machine sync *are* the version layer's remote, pointed at whatever host the user chooses — or none. What the product adds is awareness: sync state (are there unpushed changes? new commits on the remote?) and push/pull as substrate operations, so a surface can display freshness or automate the round-trip without owning any of it. One recorded wrinkle: not everything travels with the corpus remote — version-ignored personal state (machine-local config, private keys' worth of preference) may want a different channel or none; the split is config the product should leave room for rather than assume away.

## ⚖️ Tradeoffs

- **Rejected: an application-owned version history** (a database of revisions, a sync service's timeline). Couples all three trust needs to one application's lifetime and export goodwill — precisely the coupling [markdown-flavor](markdown-flavor.md) exists to forbid at the storage layer. An open version layer gives diffable history that any tool can read and any host can carry.
- **Rejected: hard-coding the VCS with no seam.** Betting a decades-scale corpus on one tool's permanence is unnecessary when the dependency can be stated as properties. The cost of the seam is low (the verbs already wrap the boundary); the cost of no seam is a migration with no abstraction to migrate behind.
- **Rejected: timer-based auto-commit as the default.** A commit whose message a timer wrote records that time passed, not what happened; the history degrades from a journal into a trace, unreadable by exactly the provenance queries multiplayer needs. Deliberate, content-derived units are what make history worth having — cadence *automation* is fine as config, but the unit must remain semantic.
- **Rejected: commit-on-completion.** Holding work out of history until it's finished creates a class of long-lived invisible, unprotected edits — unauditable by other writers and lost to any failure. Early, incremental commits cost nothing (the deferred-completeness gates make unfinished work committable) and buy the note's actual evolution as a record.
- **Rejected: whole-tree commits as the write verbs' behavior.** In a single-writer world "commit everything dirty" is convenient; in the assumed multi-writer world it silently attributes one hand's work to another — corrupting exactly the provenance this PDR exists to establish. Scoped commits are invariant; whole-tree remains available as an explicit human act outside the verbs.
- **Rejected: parallel authorship metadata** (author fields maintained in the notes themselves). A second bookkeeping surface that every writer must service and any writer can forget — it drifts from the truth the version record already carries for free.
- **Rejected: requiring ownership of the version boundary.** Symmetric with guest mode: a product that only works when its hooks run excludes embedded corpora, and gains nothing — its read surface never needed ownership, and its checks can run advisory anywhere.
- **Tension carried, not resolved:** history is only as good as the posture that wrote it, and both the hooks-not-hardcoded stance and guest mode mean the product cannot *guarantee* the discipline — a vault with lax config or a host-owned boundary accrues a poorer journal. The product makes the disciplined path the default and the degraded paths legible, not impossible.

## 🖥️ Surfaces

The history verbs and the write posture are substrate; surfaces differ in what they render and whether they write.

- **TUI (read-side).** The per-note history view — the one capability kept from every richer-client ambition (the incumbent tooling dropped its in-app commit client; the history *viewer* was the genuine plus). Its abstention from commit affordances is a per-surface choice, not the product stance.
- **CLI / SDK (the owned write path today).** Metadata verbs commit validated, pathspec-scoped, typed changes (staged-scope check with rollback); agent write verbs commit immediately on write with actor-typed messages, making the log a per-actor journal; the boundary gates ride the hooks; draft-state makes unfinished work committable. Merge posture preserves per-commit attribution (rebase, never squash — the audit trail is the point).
- **MCP.** Remote agents ride the same verbs (including deferred-commit chaining), so provenance survives remoteness; history and attribution are queryable fields, not local privileges.
- **GUI editor (fallback).** Writes files and knows nothing of git — the terminal commits behind it. Standing evidence that surface and version layer decouple cleanly: the fallback edits, the substrate versions.

# Note types: one class per note, flavor as tags

- **Status:** adopted (interview-first rewrite confirmed 2026-07-22; the two-level model is lived daily — the location and policy-hook stances lead the substrate, see Notes); amended 2026-07-30 — roles generalized to capability sets (see Design; the amendment's packet lives in the maintainers' private planning record)
- **Decided / updated:** 2026-07-22; amended 2026-07-30 (capability sets)
- **Layer:** both — the substrate defines and enforces the taxonomy; surfaces template, validate, and browse by it
- **Config vs. invariant:** *Invariants* — every note carries exactly one type; classes are few and own structure; flavor variation is tags, never new classes; the substrate attaches behavior to declared **capabilities** rather than to type names, and a corpus must declare exactly one catch-all; location carries no meaning. *Config-points* — the taxonomy's contents (which classes and subtypes exist and what each requires — canonical home: each vault's committed contract, validated by the SDK's contract types (`crates/dogtag`, forthcoming — see [Architecture](../../architecture.md))), which types carry which capabilities, all type names, and each type's edit policy.

## 👁️ Intent

A note's type is what the system understands about it; everything else the system does hangs off that understanding. The claim the design defends last: **the author of a note cannot be relied on to remember, at the moment of capture, every question that kind of note needs answered.** The type carries the questions — the required fields, the body scaffold — so notes are complete by construction rather than by memory or discipline. Four jobs follow, and they hold for any knowledge base and any author, human or agent:

- **Structure.** The type stamps the shape: which frontmatter is required, how the file is named, what sections the body opens with.
- **Validation.** A note can only be checked against a schema if the system knows which schema applies; the type is the dispatch key.
- **Findability.** The type is the first facet of every browse, group, and filter (consumed by [search-and-filter](search-and-filter.md)).
- **Consistent authoring at scale.** An agent — or a second human — writing into the knowledge base needs the same answer every time to "what does this kind of note look like." The type is that answer; it's what keeps many authors converging on one shape instead of drifting apart.

One growth requirement bounds the design: adding a new *flavor* of note must never require a schema migration or touching every consumer.

## 🎨 Design

A two-level type system on a single discriminator:

- **One type per note, one field.** Every note carries exactly one type, in one frontmatter field. The class set is small and deliberately bounded; each class owns *structure* — required frontmatter, filename shape, body template.
- **Flavor is a subtype tag.** Variation within a class lives in tags in the class's tag namespace (a workout log vs. a meditation log: one log class, two tags), not in new classes. Some subtypes are required by their class, others optional.
- **Class is structure; tag is content.** The two levels are two different axes on a note: the class says how it is *shaped*; tags say what it is *about*. Neither expresses the other.
- **The litmus follows from what is schema'd.** A note's structure — frontmatter, name, template — is schema'd; its body content is not. So a flavor earns a new class only when its *structure* diverges enough to need its own template; a flavor that differs only in content is a tag on an existing class.
- **The taxonomy lives in the substrate.** Which classes and subtypes exist, and what each requires, is defined once (canonical home: each vault's committed contract, validated by the SDK's contract types (`crates/dogtag`, forthcoming — see [Architecture](../../architecture.md))). This PDR never enumerates them, per the [shared-definition rule](README.md#shared-definitions--one-home-everyone-links).
- **Behavior binds to declared capabilities, not to type names.** *(Amended 2026-07-30 — this bullet previously described a two-role kernel binding one type per role.)* Each type declares zero or more **capabilities**, and the substrate attaches behavior to those declarations; every type is otherwise structure config it templates and validates but doesn't interpret. Two capabilities are foundational. **Identity-bearing** marks the notes the knowledge base is *about*: proxies for things with identity outside the base — people, places, organizations — which many notes reference and whose references must *converge* (aliases resolved, duplicates merged, external datasets bound to one canonical node). These are what entity resolution targets and what structured relationships connect ([relationships](relationships.md)). **Catch-all** marks the bottom type: capture must never block on classification, so there is always a class that accepts anything. A third, **closed-write**, is the policy hook below.
- **Capabilities are sets, and cardinality is part of the contract.** A knowledge base may be *about* several kinds of thing — a corpus with distinct person, place, and organization classes has three identity-bearing types, not one privileged "entity" type with two impostors — so identity-bearing admits any number, including none. Catch-all admits exactly one, because a bottom type that isn't unique isn't a bottom type: capture would have to choose, which is the blocking the capability exists to prevent. Binding by capability rather than by name is what lets the substrate ask a question it can answer across any corpus — *which types here bear identity?* — instead of demanding that every corpus agree on a word.
- **Location carries no *taxonomic* meaning.** Every markdown file under the vault root is indexed, whatever folder it sits in; folders are ergonomic convenience, never a type system. The path is never written into the file — a stored path drifts on every move — and is shown and queried like frontmatter. What the path *does* carry is identity: it is what distinguishes two notes that happen to share a name, so a bare-name link resolves only where the name is unambiguous (identity model: [markdown-flavor](markdown-flavor.md), amended 2026-07-30). Folders classify nothing and identify everything.
- **Type is the hook for edit policy.** Who may write a note of a given type — no one, humans, agents, named authors — is config keyed by type. Immutable source material is therefore *a type with a closed edit policy, not a separate place or layer*: "immutability" is policy on a class, and layer models dissolve into the type system. The permission and provenance semantics themselves (defaults, enforcement posture, how authorship is resolved) are their own product decision; this PDR fixes only that the type is the key they bind to.

A best practice rather than a rule: when a subtype needs its own data, prefer inline typed links in the body over per-subtype frontmatter — the schema stays subtype-agnostic and a new subtype field causes zero template churn. Guidance, not enforcement; the system shouldn't hard-restrict it. (Typed-link semantics: [relationships](relationships.md).)

## ⚖️ Tradeoffs

- **Rejected: a class per flavor.** Every consumer of the taxonomy — the template library, the validator, the picker, every agent's instructions — scales with the class count, so classes that differ only in content charge a structural price for a distinction tags express for free. And a taxonomy too large to hold in one's head stops being applied consistently, which defeats the purpose of having one.
- **Rejected: one catch-all class, everything as tags.** Dissolves structure ownership — no required fields, no template, no validation target — and capture completeness collapses back onto author memory. Over-consolidation fails the Intent the same way sprawl does, from the other side.
- **Rejected: multiple types per note (mixins, composition).** Composition rules, precedence, and template merging are complexity every user must internalize and every consumer must support, purchased for cases one class plus tags already covers. The best systems are simple systems.
- **Rejected: a role map binding one type per kernel role.** *(Amendment, 2026-07-30.)* A map from role to type name is the obvious way to let a corpus rename what the substrate depends on, and it is enough only while each role has exactly one occupant. It breaks on the ordinary case of a base that distinguishes people from places from organizations: the map forces one of them to be *the* entity and demotes the rest to types the substrate no longer recognizes as identity-bearing, which silently narrows entity resolution to a third of the corpus it should cover. Capabilities-as-sets cost one word of vocabulary and remove the ceiling.
- **Rejected: reserved canonical type names with renaming as presentation only.** *(Amendment, 2026-07-30.)* If the substrate owns the names and a corpus merely relabels them for display, the taxonomy is the product's rather than the corpus's — and the first knowledge base whose real structure doesn't map onto the reserved set has to distort itself to be legible. The type system's whole claim is that structure is the author's to define; reserving names retracts it.
- **Rejected: a dedicated subtype schema axis** (a `subtype:` field with its own enums and rules). A second schema axis for what tags already express; subtype-as-tag stays queryable through the same tag tooling every surface already has.
- **Rejected: meaning-bearing locations** — folders as taxonomy, or purpose-based directories ("the immutable sources folder") as a de-facto layer model. A folder taxonomy is a second, weaker type system: single-assignment, invisible to metadata tooling and validation, and silently rewritten by every move. Once one discriminator is authoritative, location-borne meaning can only compete with it or drift from it; what location used to encode (mutability, provenance) is expressed as per-type policy instead.
- **Tension carried, not resolved: the class/tag line moves.** A flavor can graduate to its own class when its structure diverges enough — the litmus re-applied per case, deliberately a judgment call rather than a fixed rule.

## 🖥️ Surfaces

The type system is substrate-enforced and UI-independent; surfaces consume it differently.

- **CLI / SDK (authoring — where type is enforced).** Note creation stamps template + required frontmatter + the discriminator; the lint fails any note whose `type:` is missing or malformed; completion offers the valid class/subtype enums; the CLI prints the live schema.
- **TUI (consumption).** Type drives faceted browse, grouping, and the type-sectioned index ([search-and-filter](search-and-filter.md)); displays the type, doesn't author it.
- **MCP.** Type is a filter and a return field — `list`/`search` scope by class and subtype; the same taxonomy with programmatic and remote reach.
- **GUI editor (fallback).** Reads the discriminator to bind each note to its class-level fields and views.

## Notes

- Receipts (corroborating, not the argument): in the incumbent corpus, both rejection stories were lived before this design settled; a single kebab-case `type:` field became the sole on-disk discriminator; and the litmus has been applied in anger — four kinds of work on one project class, split by an optional subtype tag.
- The location and policy stances lead the substrate: the incumbent corpus still expresses source-material immutability as a place (a dedicated directory). Executing this PDR implies a superseding decision plus a migration to a source *type* with a closed edit policy; until then the directory is the mechanic and this PDR is the position.
- The authorship/permission semantics the policy hook binds to were deliberately left undrafted here; they were designed multi-author-first (authorship resolved from version-control history) and are now frozen in the [authorship](authorship.md) PDR, which consumes the type key this PDR fixes.

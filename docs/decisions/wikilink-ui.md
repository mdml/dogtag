# Wikilink UI: links resolve to a presentational identity; what to show is the surface's call

- **Status:** adopted — interviewed, drafted, and adopted 2026-07-29
- **Decided / updated:** 2026-07-29
- **Layer:** both — the substrate defines the resolution contract; surfaces render and bind gestures over it
- **Config vs. invariant:** *Invariant* — resolving a link is a **substrate operation with one answer**, never per-surface re-derivation; the resolution returns the target's **presentational identity** (name-set, type, lifecycle state, representative image); **unresolved is a first-class resolution outcome**, not an error; a link's display is **derived at read time**, never a second stored fact (the authored alias being the one deliberate exception); the interaction capabilities — resolve, inverse, target-content fetch, mint-from-reference, name-based candidate lookup — are **substrate operations every surface builds on**. *Config-point* — which name a surface displays and every other presentation choice (modes, color/glyph encodings, gestures — all per-surface); the alias-constraint level (arbitrary prose ↔ restricted to the target's own name-set); whether external-target resolution (URL unfurl) is enabled; candidate ranking.

> **Boundary.** [markdown-flavor](markdown-flavor.md) owns link *syntax* and the identity model (filename as stable identity, title as free-to-change display); [relationships](relationships.md) owns link *meaning* (predicates, direction, the derived inverse); [note-types](note-types.md) owns the type vocabulary a link's target wears. This PDR owns the layer above all three: how an authored reference becomes something a reader sees and acts on.

## 👁️ Intent

A link's value at read time is the *target's* identity surfaced in place: what it's called, what kind of thing it is, whether it can still be trusted, whether it's worth traversing. A reader should never have to parse an address to know what a reference points at — but a knowledge system is read through many surfaces (a terminal, a GUI, an agent, the bare file), and each has different affordances for showing that identity. The user needs every surface to *agree on the facts* about a link's target while staying free to present them in whatever form the surface does best.

## 🎨 Design

**The product decision is what resolution returns, not what any surface shows.** Resolving a link is a substrate contract: given a reference, return the target's **presentational identity** — its full name-set (display title, stable identity/slug, registered aliases), its type, its lifecycle state, and a representative image if it has one (a person's face, a work's cover). Every question a renderer could ask — what do I call this, how do I color it, should I badge it as archived, can I show an avatar — is answered from that one bundle, computed once in the substrate rather than re-derived by each tool. What a surface *does* with the bundle — which name it shows, whether it encodes type as color, whether "display modes" exist as a user toggle — is wholly per-surface configuration. The product deliberately names no default rendering: prescribing one would couple the product to the surfaces that can honor it.

**Unresolved is a first-class outcome.** The store is plain files, mutable by any tool or none ([markdown-flavor](markdown-flavor.md)) — so resolution can never assume integrity. Even a system that makes dangling references unwritable through its own surfaces must handle the file deleted or renamed behind its back. Resolution therefore returns "unresolved, here is the raw reference" as an ordinary result, letting any surface render the state distinctly and offer repair; the corpus-hygiene arm (validation that committed links resolve) is the substrate's lint, and the two together cover the window authoring passes through.

**The alias is the one authored display fact — and how free it is, is config.** A link may carry an author-supplied display text that overrides derived naming. Because display everywhere else is derived, this is the single place display text is *stored* — so the product makes its looseness a knob: a vault may allow arbitrary prose (the alias as grammatical fit inside a sentence), or constrain alias text to the target's own name-set (title or registered aliases), so that every rendering of a note's name is one the note itself claims. Two consequences of the substrate knowing the name-set: alias **drift is derivable** — an audit can list links whose display text no longer matches any of the target's names, with acting on it the user's call — and **name changes propagate on offer**: just as identity renames are substrate-mediated link rewrites, a title or alias change offers to update the potholes that matched the old name, never silently.

**The contract extends to non-note targets.** A reference to something outside the corpus — an external URL, an attached file — resolves under the same contract: the substrate fetches what presentational identity the target offers (a page title and favicon; a file's kind and name) so surfaces can render external references as richly as internal ones. Whether external resolution is enabled is config — it requires the network, which not every deployment wants in its reading path.

**Interaction is a capability set, not a gesture set.** The product owes substrate operations sufficient for every link interaction a surface might bind: resolve (follow), the derived inverse (backlinks — [relationships](relationships.md)' contract, consumed here), fetching the target's content (peek/preview without leaving the current note), minting a note from an unresolved reference (link-first creation), and a name-based candidate query — match against the full name-set, return bundles — so that inserting a link is an act of *resolving a real note by any of its names*, not typing an address. Which of these a surface exposes, and behind what gesture, is the surface's design. One deliberate split inside the set: a target's **neighborhood** — its forward links and its derived inverse — is its own query, not a field of the resolution bundle. The bundle is the cheap per-link answer on the render path, where a displayed note resolves many links at once; the neighborhood is a traversal question about one target, asked when the user turns toward it. Folding the graph into every resolution would tax the common case with queries it doesn't need.

## ⚖️ Tradeoffs

- **Rejected: the product prescribes a canonical rendering** (always show the title, always color by type, a blessed mode vocabulary). Surfaces differ too much — a terminal, a GUI, an agent consuming JSON, and `cat` on the bare file cannot honor one rule, and a rule written for the richest surface quietly becomes false everywhere else. The durable product layer is the *facts* about the target; rendering commitments belong to each surface's own design.
- **Rejected: per-surface resolution.** Letting each tool derive display names, types, and states from the files itself multiplies resolvers that drift apart — two surfaces disagreeing about what a link is called or whether it's broken is corrosive in a way no rendering difference is. One substrate answer, many presentations.
- **Rejected: baking display text into every link at insert time** (denormalizing the title into the file so no resolution is needed). Stored display text is a copy of a fact that lives elsewhere; copies drift, and a corpus-wide title change becomes a corpus-wide edit. Derived display cannot drift. The authored alias survives as the deliberate, bounded exception — chosen per link by the author, not imposed as the mechanism — and whether a link carries one is the author's call per link, with no product pressure either way.
- **Rejected: treating dangling references as impossible or as errors.** A plain-text store guarantees out-of-band mutation; a resolution contract that throws on missing targets forces every surface to invent its own broken-link handling — the per-surface-resolution failure again, in its ugliest corner.
- **Rejected: an internal-only contract.** External references are part of real notes; leaving their presentation entirely to surfaces re-creates per-surface resolution for the target kind where inconsistency is most visible. The same bundle idea covers them; the network dependency is the reason it's switchable, not a reason to exclude it.
- **Tension carried, not resolved:** with no prescribed rendering, nothing guarantees surfaces converge enough that a user moving between them feels one product. The bet is that one shared bundle naturally converges presentation where it matters (names and states agree everywhere) while leaving the rest to each surface's strengths.

## 🖥️ Surfaces

The bundle and the capability set are substrate; each surface picks its rendering and gestures.

- **TUI (reading).** Renders links as prose, not source (brackets stripped, alias honored); today's bare-link display is a humanized slug — the degraded fallback, with the title-in-the-index column the named substrate gap; type and status already color list rows from the same vocabulary the bundle would carry; backlinks as a pane.
- **CLI / SDK (authoring).** Editor completion is the candidate query in practice — matching basenames and frontmatter aliases, inserting the `[[slug|Alias]]` form (markdown-oxide in the incumbent tooling); the link lints (body and frontmatter) are the committed-corpus arm of unresolved handling.
- **MCP.** The bundle's fields are return fields — an agent reading a note gets targets with names, types, and states, and `backlinks` is already a first-class tool; the same contract, programmatic.
- **GUI editor (fallback).** The incumbent editor is the precedent for name-set display (H1 as display identity) and for presentational richness from structured links (labeled typed inverses).

## Notes

- **Interview record:** 2026-07-29, the interview-first pass. The load-bearing reframing, adopted verbatim in spirit: *"isn't the question what the SDK returns?"* — every presentation question asked (default display, color channel, display modes, verbs) got the same answer: the substrate provides the facts and operations; the UI decides. The PDR's whole shape follows from that. Also from the interview: the representative-image field (a note's profile photo in the bundle, so UIs can render avatars in links) and the URL-unfurl extension (in as the same contract, enablement config). Adoption was conditioned on the neighborhood (forward links + backlinks of a target) being available through the substrate — settled as a second query beside the bundle, per the Design's render-path argument.
- **Substrate follow-ons (recorded seams, not built):** the title-indexed column (already on the pull-driven backlog); the alias-constraint lint knob; the representative-image and unfurl fields of the bundle. The posture: record the seam, build on pull.
- The `[[slug#heading]]` unvalidated-anchor lint gap is homed in the maintainers' private planning record; heading anchors ride the same resolution contract when pulled.

# Search & filter: faceted browse, not a query builder

- **Status:** adopted — the doc set's exemplar, written first (2026-06-17); generality pass to the for-any-PKM bar 2026-07-29 (the voice rule postdates the original)
- **Decided / updated:** 2026-06-17; revised 2026-07-29
- **Layer:** both — the substrate provides the index and the facet vocabulary; surfaces present them
- **Config vs. invariant:** *Invariant* — the retrieval model is **faceted browse + search (lexical and semantic) + graph queries + sort + group**, never an arbitrary boolean filter builder; retrieval reads **canonical precomputed indexes**, not live scans; facets are **the authored schema surfaced**, never a parallel retrieval vocabulary; **saved views are user-definable configuration over substrate signals**, not compiled-in features; search and type-to-filter carry **per-intent defaults** (search widens, filtering narrows). *Config-point* — the facet vocabulary itself (it *is* the schema — canonical home: each vault's committed contract, validated by the SDK's contract types (`crates/dogtag`, forthcoming — see [ARCHITECTURE](../../ARCHITECTURE.md))); the indexed columns, ranking weights, and embedding model (canonical home: the index — see Notes); the sortable/groupable field set (the indexed metadata, same home); the roster of saved views; each surface's interaction idiom.

> **Boundary.** This PDR owns *retrieval*: anything that takes the corpus and returns a **set** the user then browses. The demarcation with the link PDRs is by question answered: [relationships](relationships.md) defines what the graphs *are* (the note digraph, the entity lens); [wikilink-ui](wikilink-ui.md) owns acting on *one* reference (resolve, follow, peek, its neighborhood as an interaction); set-returning graph queries live here. The facet vocabulary is [note-types](note-types.md)' and the schema's; lifecycle states and flags arrive as facets from [lifecycle](lifecycle.md); the **view** concept defined here is what [inbox-workflow](inbox-workflow.md) consumes ("there is no inbox — there are views").

## 👁️ Intent

Get to the right note — or the right *set* of notes — at the speed of thought, by **leaning on the structure the corpus already carries** (type, state, tags, dates, links) rather than reconstructing it as queries. In a knowledge system whose authoring investment is rich, validated structure — whether authored by the user or by agents on their behalf — retrieval is where that investment pays out or doesn't: a surface that makes the user *construct a query* to use their own structure has wasted it, and a surface that ignores the structure (bare text search) has discarded it. Both retrieval failures tax every single lookup, and lookups are the most frequent act in a knowledge system's life.

## 🎨 Design

**Retrieval operates over the corpus's real representation.** A structured knowledge corpus is two graphs plus attributed notes: notes as nodes with links as edges, and the derived entity lens (identity-bearing nodes, with notes and relationships as labeled edge evidence) — [relationships](relationships.md)' model — where each note carries attributes (type, state, tags, dates, content). The retrieval moves below are the common operations on that representation, exposed at speed; they are one family because their results all land in the same browsable set, where the other moves compose.

Five composable moves, with a searchable picker as the entry point to any facet value:

- **Faceted browse** — the authored vocabulary presented as a browsable index with counts (notes per type, per tag, per state, per date bucket); pick a value to drill in. Facets are the schema surfaced — a vault with a different schema gets different facets for free, because there is no second, retrieval-only vocabulary to maintain.
- **Lexical search** — ranked full-text over a canonical precomputed index. Which fields are indexed and how they're weighted is substrate config with one canonical home (see Notes); the product behavior is only "search reads an index, never scans the corpus" — the property that keeps retrieval instant at any corpus size.
- **Semantic search** — recall by meaning, beside recall by phrase. People cannot reliably remember the exact words they used, and for that whole class of lookups embedding-based retrieval simply outperforms lexical matching — so it is a core retrieval move, not an add-on: a second derived index (embeddings) behind the same search surface, with the embedding model and the lexical/semantic blend as config.
- **Graph queries** — set-returning operations on the two graphs: the neighborhood of a note as a filterable list, a note's dependency closure, the notes evidencing an entity pair. The graphs are relationships' model; *querying them into sets* is retrieval, and the resulting sets take facet-narrowing, sort, and group like any other.
- **Sort** and **group** — order the current set by, and section it under, the indexed metadata (recency, date, name, type, state). The available fields are the index's, not enumerated here.

**Multi-facet AND-narrowing** (type ∧ state ∧ tag ∧ date-bucket) is in scope: it is *narrowing along authored facets*, which is categorically different from a freeform filter builder — every step picks a value from a vocabulary the user already knows, rather than composing boolean structure. A **searchable picker** is the entry point to any facet's values: one interaction shape for every vocabulary, replacing per-facet bespoke controls and blind cycling.

**Saved views are configuration, not features.** A view is a named, user-definable combination of the moves above (facets + query + sort + group) over substrate signals — cheap to define, cheap to discard. This is the mechanism [inbox-workflow](inbox-workflow.md) leans on for its "no inbox, only views" stance: any privileged-seeming lens ("Needs triage", "Drafts", "This week") is just a saved view, and because view *definitions* read substrate signals, every surface and agent computing a view gets the same answer.

**Two intents, two defaults.** A *search box* and a *type-to-filter* are different acts and deserve opposite defaults: search is recall-oriented (a broad match set, ranked — additional terms should widen or re-rank), while filtering is precision-oriented (each keystroke and each added token should *narrow*). This is a product stance for two reasons: it matches the convention every user already carries from everywhere else (search boxes recall, filters narrow — fighting that expectation taxes every use), and it dramatically simplifies the engineering — each path optimizes for its one semantic instead of one mechanism serving both badly. One substrate serves both; the divergence is deliberate and per-intent, not an inconsistency to unify.

## ⚖️ Tradeoffs

- **Rejected: an arbitrary AND/OR filter builder.** A query builder asks the user to re-express, in boolean algebra, structure the corpus already holds — authoring-surface complexity relocated onto a consumption surface, paid on every use. Where structure is rich and validated, the named moves dominate: real retrievals decompose into facet steps, text, and graph hops, and what little the builder's extra expressiveness serves is better asked of the substrate directly than encoded as UI. *(Receipts, corroborating: a GUI daily-driver with no arbitrary-filter affordance was never missed for one, and a live trial confirmed arbitrary filtering never reached for.)*
- **Rejected: search-only retrieval.** Bare full-text treats a structured corpus as a bag of words — discarding exactly the typed, validated metadata the system invests in authoring. Facets and graph queries are the payoff of that investment; a retrieval surface without them makes the schema decorative.
- **Rejected: lexical-only search.** Exact-phrase recall assumes the user remembers their own words, and for a corpus written across years — partly by agents — they often won't. Treating semantic retrieval as an optional add-on leaves the most human failure mode (I know it's in there, I can't name it) unserved by the core product.
- **Rejected: an embedded query language in notes.** Coupling retrieval to a query dialect embedded in the corpus makes every note a potential program: a parsing burden for every future tool, a cognitive tax on every reader, and a maintenance liability when the dialect shifts — the [markdown-flavor](markdown-flavor.md) admission test fails on all counts. Queries belong in configuration (saved views) and surfaces, not in the store. *(Receipt: the incumbent corpus evicted embedded query blocks on exactly this ground.)*
- **Rejected: hard-coded views.** Compiling the useful lenses into a surface makes the lens roster a development act, when which lenses matter is a per-person, per-season fact. Views as data — definable at runtime, over substrate signals — keep the roster where it belongs. *(The compiled-in form was the recorded friction that filed this seam.)*
- **Rejected: one unified match semantic across search and filter.** Superficially cleaner, but it forces one of the two intents to fight its default on every use — a broad-match filter never narrows; a narrowing search box hides recall. Per-intent defaults over one substrate cost nothing and fit both.

## 🖥️ Surfaces

The Intent and the "facets + search + sort + group, never a builder" stance are UI-independent; surfaces differ in idiom and entry point.

- **TUI** — the navigation surface this decision most shapes: faceted narrowing, searchable facet picker, sort/group, full-text — measured instant at full corpus scale; type-to-filter narrows (implicit AND, prefix on the active token) per the two-intents split.
- **MCP** — faceting as tool parameters over the same substrate (`search` / `list` / `tags`), programmatic and remote. The no-builder invariant holds shape here too: the tools stay facet- and search-shaped, not a SQL passthrough.
- **CLI / SDK** — the search box (broad-match ranked search) and name resolution as the scriptable entry points.
- **Tolaria (GUI fallback)** — the cross-surface confirmation: faceted sidebar, saved views, full-text — the same model in GUI chrome, evidence that the model, not the chrome, is what matters.
